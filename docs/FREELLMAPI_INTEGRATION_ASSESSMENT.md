# FreeLLMAPI Integration Assessment and Adoption Plan

**Assessment date:** 2026-10-23  
**Repository reviewed:** https://github.com/tashfeenahmed/freellmapi  
**Reviewed release:** v0.16.8 (latest release observed on 2026-10-23)  
**Decision:** suitable for a controlled, optional development fallback; not a production reliability guarantee.

## Executive assessment

FreeLLMAPI is a self-hosted, OpenAI-compatible gateway. It can consolidate provider credentials behind one local API, select among configured provider/model endpoints, track provider quotas, and fail over when upstream providers become unavailable or rate-limited. Its feature set also includes tool calling, multimodal endpoints, a dashboard, and optional multi-model synthesis ("fusion").

For Agent Team Starter, the highest-value first step is **not** to replace the existing router or make every stage call multiple models. Instead, add FreeLLMAPI as an optional adapter behind the current provider abstraction. Keep the current Gemini and OpenRouter paths intact, disable FreeLLMAPI unless explicitly configured, and run all tests without live provider calls. This provides a reversible integration and avoids tying the project to one gateway.

## Findings verified from upstream project documentation

- The public repository uses the MIT license.
- The API is OpenAI-compatible and documents `/v1/chat/completions`; the default local setup uses port 3001.
- The router maintains a model catalog, tracks rate limits/health, and can fall back between configured upstream endpoints.
- Provider API keys are stored in a local SQLite database and encrypted at rest by the application; they are decrypted in memory for upstream calls.
- The upstream project describes itself as local-first and single-user. It explicitly advises against exposing the service directly to the public internet.
- The project documents no SLA, variable latency, quota exhaustion/degradation, and changing free-tier availability.
- Fusion fans a prompt out to multiple models and uses a judge model to synthesize an answer. This increases upstream requests, latency, and quota consumption and should not be the default for every agent stage.
- The latest release observed during this assessment was v0.16.9. Pin and review a specific release rather than blindly pulling `:latest` for a repeatable setup.

## Recommended architecture for Agent Team Starter

1. Keep the existing `FreeFirstRouter` as the orchestrator; do not make the project depend on FreeLLMAPI being installed.
2. Add a small OpenAI-compatible adapter configured only through environment variables:
   - `FREELLMAPI_BASE_URL` (default for a local installation: `http://127.0.0.1:3001/v1`)
   - `FREELLMAPI_API_KEY` (the local unified key generated by the FreeLLMAPI dashboard)
   - `FREELLMAPI_MODEL` (default: `auto`; allow a named profile such as `auto:fast` only after validating that profile on the installed version)
3. Activate the adapter only when its key is present. Do not make network requests during configuration checks, tests, or offline benchmarks.
4. Use it as a fallback after the direct Gemini attempt and before/alongside other configured fallbacks; keep provider order explicit and observable in the trace.
5. Send system instructions as a separate `system` message. Keep task and retrieved text marked as untrusted data.
6. Bound request timeouts, prompt/output sizes, and retries. Avoid nested retry storms: the app should retry at most once for transient errors while the gateway handles its own bounded upstream failover.
7. Log only provider/model identifiers, latency, status category, and output length. Never log prompts, responses, API keys, authorization headers, or full raw provider error bodies.

## Safe setup policy

- Run FreeLLMAPI on the same machine as the agent when possible, bound to loopback (`127.0.0.1`), not `0.0.0.0`.
- Never publish port 3001 to the internet. The gateway is documented as single-user and is not a multi-tenant service.
- Generate and preserve a strong `ENCRYPTION_KEY`; protect the database, `.env`, backups, and dashboard access. Do not commit credentials or paste them into notebooks/logs.
- Prefer a pinned release and review the release notes and image provenance before updating. Do not pipe a remote install script directly to a shell without inspecting it first.
- Add only provider accounts whose terms permit the intended personal/internal use. Do not assume that “free” means unlimited, commercial use is permitted, or reselling/redistribution is allowed.
- Do not put private customer data, secrets, production credentials, or sensitive personal data into third-party free-tier models unless the provider's data handling and terms have been reviewed.
- Treat all model output as untrusted. It must not gain tools, shell access, credentials, browser access, or authority to perform side effects merely because it came through FreeLLMAPI.

## How to maximize useful capability without wasting quota

### Routing profiles
Use a fast/cheap route for planning and routine drafting, a stronger route for tasks where reasoning quality matters, and a vision-capable route only when images are actually present. Verify profile names and model capabilities against the installed gateway's `/v1/models` output; catalog names and free quotas change.

### Selective synthesis
Do not use `fusion` for every Planner → Executor → Reviewer stage. First measure the single-model baseline. Use fusion only for high-impact, ambiguous tasks where independent candidate answers are valuable; compare the result against a single-model run and record additional latency and quota use.

### Evidence and review
A model-based reviewer is not an independent verifier. For code changes, require tests, static/security checks, source citations where factual claims matter, and human approval for release decisions. Multiple models can share the same blind spot.

### Reliability and quota accounting
Track successful requests, rate-limit errors, fallback count, latency, token use, and task success. Do not optimize on tokens alone: measure quality per successful task and cost/quota per accepted result. Expect free-tier availability to vary through the day.

## Acceptance checklist before relying on it

- [ ] Local installation starts and dashboard is bound to loopback.
- [ ] A harmless test prompt succeeds using a provider key explicitly configured by the owner.
- [ ] `/v1/models` confirms the chosen model/profile is available.
- [ ] Unit tests verify URL handling, system-message separation, empty/malformed responses, secret redaction, and fallback behavior without making network calls.
- [ ] Offline tests and security scans pass with FreeLLMAPI unconfigured.
- [ ] A short, owner-approved live test records latency, quota behavior, fallback behavior, and data handling.
- [ ] Provider terms and data policy are reviewed for intended use.
- [ ] No public exposure, paid calls, or production claims are made from an offline test.

## Non-goals

This integration does not guarantee zero cost, permanent free access, frontier-model quality, correct answers, prompt-injection immunity, privacy equivalence across providers, or production uptime. It is a routing option—not a substitute for model evaluation, application security, or operational controls.
